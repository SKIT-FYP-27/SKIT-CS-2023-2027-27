# Migrations

## Why this looks a little different from a normal Prisma project

Normally `prisma/migrations/` is built up entirely by running
`npx prisma migrate dev` over and over as the schema evolves — Prisma
generates each `migration.sql` itself.

Here, `schema_v2.sql` was written and applied to the database
**before** Prisma entered the picture (Go 1 last week). So Week 2's
job isn't "create a migration for a new change" — it's **baselining**:
telling Prisma Migrate "this schema already exists, here's the
migration history to treat as already applied."

`0_init/migration.sql` in this folder was generated by taking a
`pg_dump --schema-only` of the actual, seeded database (the same one
`schema.prisma` was verified against) and reformatting it into
Prisma's own migration file conventions. It was then **replayed
against a brand-new empty database** to confirm it reproduces the
exact same schema — see the commit message / PR notes for that check.

## Commands to run once, on your own machine, against your own DB

```bash
npm install
cp .env.example .env   # set DATABASE_URL to your Postgres instance
                        # (which should already have schema_v2.sql applied)

# Tell Prisma Migrate this schema is already live — don't re-run the SQL,
# just record 0_init as applied:
npx prisma migrate resolve --applied 0_init

# From now on, any change you make to schema.prisma can go through the
# normal flow:
npx prisma migrate dev --name <describe_the_change>
```

After `migrate resolve`, `npx prisma migrate status` should report
"Database schema is up to date!" — that's the confirmation baselining
worked.
